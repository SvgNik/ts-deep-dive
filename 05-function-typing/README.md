# 05 · Function Typing

## Что изучено

- Сигнатура как два обязательства в противоположных направлениях: параметры - требование к вызывающему, return type - обещание вызывающему.
- Почему параметры не выводятся: тело описывает действия над значением, а не требования к нему. Выводить не из чего.
- Почему return type выводится: тело - единственный и полный источник.
- Момент и место проверки: аргумент против параметра в точке вызова (TS2345), тело против return type в точке определения (TS2322).
- Явный return type разворачивает направление проверки: без аннотации тело диктует тип, с аннотацией тип проверяет тело.
- `void` как «результат не предназначен для использования», не как «возвращается undefined».
- Асимметрия проверки `void`: строгая при объявлении функции, мягкая при присваивании функции типу `() => void`.
- Правило «`void` никогда не входит в union»: сузить нечем, результат не присваивается в `T | undefined`.
- Optional `?` против `T | undefined`: первое влияет на арность вызова, второе требует явной передачи аргумента.
- Default выводит тип параметра, снаружи даёт `T | undefined`, срабатывает только на `undefined` и не срабатывает на `null`.
- Rest только последний и только массивного типа; аннотируется тип коллекции, не элемента.
- Function type как именованный тип; стрелка в type space против стрелки в value space.
- Contextual typing как исключение из правила о параметрах; вынесенный из вызова callback теряет контекст.
- Overloads - на уровне знакомства: несколько сигнатур на одну реализацию, implementation signature снаружи не видна.

## Что должен уметь

- Читать сигнатуру как контракт и отвечать, где именно возникнет ошибка при несовпадении.
- Выбирать между `void` и `T | undefined` по смыслу функции, а не по наличию `return`.
- Выбирать между `?`, `| undefined` и default по тому, что должен сделать вызывающий.
- Выносить function type в именованный тип и понимать, что имена параметров внутри него - документация.
- Объяснять, почему inline-callback не требует аннотации, а вынесенный требует.
- Понимать поток управления callback: функция передаётся, вызывает её принимающая сторона.

## Сложные моменты

- **Поток управления callback.** Ты не вызываешь переданную функцию - её вызывает принимающая сторона, когда сочтёт нужным. `addEventListener` работает так же.
- **Мягкость `void` при присваивании.** Смысл правила не в том, чтобы пользоваться результатом, а в том, чтобы не писать фигурные скобки ради его выброса: `arr.forEach(n => target.push(n))`.
- **TS1016 относится к `?`, не к default.** `function connect(host: string, port: number = 3000, secure: boolean)` компилируется, но требует явного `undefined` при вызове.
- **Имена параметров внутри function type не проверяются.** Опечатка `(taks: Task) => boolean` даёт ноль ошибок компилятора.

## Notes

Коды ошибок темы: TS1014, TS1015, TS1016, TS2322, TS2345, TS2355, TS2366, TS2370, TS2391, TS2532, TS2554, TS2769, TS7006, TS18048.

Разведение трёх соседних кодов:

| Ситуация                          | Код                       |
| --------------------------------- | ------------------------- |
| `return;` при `: number`          | TS2322, на самом `return` |
| ветка проваливается мимо `return` | TS2366, на аннотации типа |
| нет `return` со значением вообще  | TS2355, на аннотации типа |

**Ключевая находка темы.** `applyDiscount` вернула размер скидки вместо цены со скидкой - 66 вместо 374 - при нуле ошибок компилятора. Оба значения `number`, типы совпадают идеально. Типы гарантируют форму, не смысл. Пятое подтверждение правила модуля.

**Второе подтверждение в той же теме:** опечатка в имени параметра внутри function type компилятором не ловится в принципе - это не его зона ответственности.
