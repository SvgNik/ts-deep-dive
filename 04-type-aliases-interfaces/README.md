# 04 · Type Aliases and Interfaces

## Что изучено

- `type` alias: имя для любого типа - primitive, union, object, array, tuple, function type.
- Alias не создаёт новый тип. `type UserId = string` это второе имя для `string`, TS сравнивает структуру, а не имена (structural typing).
- Type space и value space разделены: имя типа нельзя использовать как значение (TS2693).
- `interface`: только объектные формы. Union и primitive назвать нельзя - у выбора из значений нет полей.
- `extends` у interface: наследование полей, множественное наследование через запятую, переопределение поля несовместимым типом запрещено (TS2430).
- Declaration merging: два объявления с одним именем в одной declaration scope сливаются. Тип поля при merging должен быть идентичен (TS2717). У `type` в этой ситуации TS2300.
- Правило выбора: `type` по умолчанию, `interface` осознанно под merging, публичный контракт библиотеки или командную конвенцию. Последовательность важнее выбора.
- Intersection `&`: складывает формы, работает с любыми типами. `extends` проверяет совместимость на объявлении, `&` откладывает падение до места использования (конфликт даёт полю `never`).
- Optional `?`: добавляет `undefined` к типу поля и разрешает отсутствие ключа. Обращение требует narrowing (TS18048). Не равно `| undefined` - там ключ обязателен (TS2741).
- `readonly`: запрещает присваивание полю (TS2540). Compile-time only, shallow, не участвует в проверке совместимости.
- Проектирование модели: правило границы - выносим в именованный тип, если форма переиспользуется, или имеет имя в предметной области, или мешает читать родителя.
- Naming: существительное предметной области в PascalCase, без префикса `I` и суффикса `Type`.
- Типы hoisted, порядок объявления не важен. Рекурсивный тип обязан идти через массив или optional-поле.

## Сложные моменты

**Declaration scope - главная находка темы.** Файл без top-level `import`/`export` это script, а не module. Все его объявления попадают в global scope. Отсюда TS2393 `Duplicate function implementation` между `03-union-narrowing` и `04-type-aliases-interfaces` - два `renderStatus` и два `getRoleLabel` конфликтовали. Фикс: `export {};` последней строкой каждого файла упражнений. Побочный эффект: после превращения в модули заработал `noUnusedLocals` и вскрыл 16 объявлений без вызовов в файлах TS 02 и TS 03. Для учебных файлов правило отключено в tsconfig.

**Declaration merging работает не везде.** Сливаются объявления только в одной declaration scope - один файл или global scope. В разных модулях это два независимых типа, слияния нет. Дополнить тип чужого модуля можно только через `declare module` / `declare global` (module augmentation, формально M4/M5).

**Граница `readonly`.** Не даёт гарантии дважды: стирается при компиляции (в JS объект обычный) и не участвует в проверке совместимости - тип с `readonly` свободно присваивается типу без него, после чего поле мутируется, не выходя из TypeScript. Плюс shallow: защищает ссылку, не содержимое. Третье подтверждение правила «компилятор молчит ≠ код правильный» за модуль.

**Union нельзя пересечь с объектом.** `type X = Status & { retryCount: number }` компилируется, но значение построить нельзя - примитив пересечённый с объектом даёт непостроимый тип. Правильное решение - положить union полем внутрь объекта: `{ status: Status; retryCount: number }`. Формально discriminated union, TS 10.

## Notes

- `npm run check` проверяет проект целиком, не отдельный файл. Читать нужно сводку внизу вывода. Критерий готовности задачи - ноль ошибок в текущем файле.
- `@ts-expect-error` подавляет ошибку на следующей строке и требует, чтобы она там была. Инструмент для учебных демонстраций ошибок.
- `import type { X } from "./x"` при `verbatimModuleSyntax: true` - обычный `import` компилятор оставит в JS, где экспорта типа не существует.
- `interface Child extends Parent` невозможен, когда `Parent` не объектная форма (TS2312). `&` складывает любые типы.
- Ошибки темы: TS2312, TS2322, TS2353, TS2393, TS2430, TS2540, TS2693, TS2717, TS2741, TS6133, TS18048.
